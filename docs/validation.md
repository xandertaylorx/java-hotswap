## Automatic plain Java launch targets — 2026-10-11

The adapter previously implemented only `get_dap_binary` and `dap_request_kind`. Those hooks launch existing configurations; they do not register automatic targets. The extension now registers a debug locator and translates the Java language extension's contextual main runnable into a direct HotSwap launch scenario. Zed passes the language's preferred adapter (normally `Java`) to discovery, so the locator accepts that preference and explicitly returns `Java HotSwap`. See Zed's [locator documentation](https://zed.dev/docs/extensions/debugger-extensions) and [task inventory implementation](https://github.com/zed-industries/zed/blob/main/crates/project/src/task_inventory.rs).

Regression coverage exercises locator registration and scenario contents, rejection of unrelated tasks, automatic plain `src` discovery, default-package and packaged main resolution, multiple entry points, and output/dependency classpath construction. Real DAP launches with only `src/HotSwapTest.java` and no configuration file reload method changes with unchanged JVM PID. A second fixture selects a packaged main alongside another main. Contextual source selection is also exercised with Maven and a custom Gradle JavaExec task.

Executed results: the release suite passed 34 cases with one graphical skip (35 total); two additional contextual Maven/Gradle launch cases passed separately, giving 36 distinct passing integration cases. All 18 Rust tests passed (two extension locator tests, sixteen companion tests), along with formatting, clippy with warnings denied and native/WASM release builds. The installed local companion matches the tested release binary.

The Java language extension remains responsible for detecting contextual runnable tasks; open the main Java file to expose its launch target. Compilation and instrumentation remain in the existing companion. No project build files or debug configuration files are generated by target registration. Live Zed UI interaction remains unverified; locator hooks, WASM compilation and real companion launch/reload are tested separately.

## Compilation timing / incremental build investigation — 2026-10-11

An isolated copy of the current Minecraft project was measured with Gradle 8.10 and Java 21. Original project files were not edited or built. The 6,637-source copy took 28.332 seconds to establish relocated build state, 0.620 seconds with no changes, and 24.906 seconds after one AbstractArrow method-body edit. Gradle reported incremental compilation of 8,426 classes in 23.022 seconds plus 1.101 seconds of dependency analysis; no forced full rebuild occurred on that edit. The exact reported 64 seconds was not reproduced. See [performance.md](performance.md) for methodology, limits and upstream references.

ABI-compatible upstream edits left app compilation up to date; an ABI-changing signature edit recompiled the app and was safely rejected by standard JVM HotSwap as an atomic batch.
- Explicit incremental=false remained false in discovered compiler settings and caused an unrelated class to be recompiled, verifying that HotSwap did not override project policy.
- Existing destructive-output failure isolation, JavaExec/run argument inheritance, project/JDK discovery, Maven, plain Java, multi-module and DAP tests remained part of the release suite.
- Full release suite: 32 passed, one graphical test skipped (33 total). The graphical LWJGL lifecycle/reload test passed separately, giving 33 distinct passing integration cases. ## Stable runtime classpath / destructive-build isolation — 2026-10-11

Investigation found that successful reload generations were already immutable, but the application still launched from the original mutable build outputs. Read-only inspection of the Minecraft build showed `prepareSource` conditionally extracting sources, `applyChanges` running a script that edits Java sources, and `compileJava` depending on that preparation. No Minecraft build was run or modified for this investigation. Gradle 8.10's [incremental compile transaction](https://github.com/gradle/gradle/blob/v8.10.0/platforms/jvm/language-java/src/main/java/org/gradle/api/internal/tasks/compile/incremental/transaction/CompileTransaction.java) moves selected class/resource files out of compiler destinations before javac and may restore them after failure; even eventual rollback leaves an unsafe window for a JVM reading those paths.

The original installed companion reproduced runtime resource loss while compiling the new destructive fixture. The fixed companion isolates the JVM's class directories, resources and dependency JARs in a private byte copy before launch. Build outputs remain separate and Gradle's task graph, dependency resolution and selected JavaExec configuration are preserved. Agent roots map to the private runtime origins; reload publication still requires successful compilation. Runtime snapshots are retained until JVM shutdown and are separate from prunable reload generations.

Executed locally on macOS Apple Silicon with the rebuilt release:

- The destructive fixture passed under Gradle 8.10 with Java 21 and Gradle 9.1 with Java 25. Its prepareSource/applyChanges pipeline deleted class output directories, resource output and a generated dependency JAR, paused before compileJava, and then failed on a duplicate method. Previously unloaded project classes, anonymous inner classes and JAR classes loaded during that window and after failure; resource reads continued.
- A prior successful method reload stayed active after failure, the same JVM PID survived, the reload commit did not change on failure, and every runtime file remained byte-for-byte identical. Repairing the source while keeping destructive regeneration enabled successfully redefined the method in that same JVM.
- Shutdown removed the runtime copy. Rust tests also verified independent copies after in-place file mutation/deletion, classpath order/origin mapping, cancellation cleanup, materialized symlinks and cycle rejection.
- The full release suite ran 30 cases: 29 passed and the graphical case was skipped. The graphical LWJGL lifecycle/reload test passed separately, giving 30 distinct passing integration cases. Existing Gradle/Maven/plain, multi-module, JavaExec argument inheritance, nested build, DAP, cancellation and structural rejection/recovery cases passed.
- Fourteen Rust tests, formatting, clippy with warnings denied, the native release build and wasm32-wasip2 release build passed. The local installed companion was replaced with this release.

The Minecraft world itself and live Zed UI were not exercised. Classes first loaded later use launch-time bytes; newly added classes and resource/dependency changes require a restart. Files accessed directly through the working directory remain project-controlled. Native Windows remains unverified.
